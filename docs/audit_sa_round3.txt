WHAT CHANGED (details in the response file)
- Books (class B'): the snapshot (idle USDC, idle HYPE, each tracked position's liquidity) is never read back from the
  account after a module action. The module adds its own effect, computed from state the account cannot write: PoolManager
  slot0 and position info BEFORE the action plus the liquidity it asked for (adds rounded up, removals rounded down, plus
  uncollected fees), the SwapExecutor's per-payer transient record (exactly one new swap, received >= minOut), the
  verified recipient delta of a transfer, the deposited amount. Claim: live - snapshot is exactly the client's own flow,
  inside or outside a bracket. sync books it valued with the SAME function and SAME price as value() (the anchor), and
  only while the anchor is trusted; otherwise it stays pending. Claim: a client flow cannot change profit.
  Removed: _snap, _post, _conserved, _checkAdd, the min/max booking price. Registration books nothing; deposit / onboard
  book USDC at face value. Removals remove only min(requested, snapshot) as booked liquidity.
- Fee: needs a trusted anchor, syncs first, charges on min(V(anchor), V(pool)) - contributed.
- Price trust (class D'): lastPriceClipped() is a view (anchor outside the band of the keeper's last report) and clears
  itself; fresh = age <= maxPriceAge, not clipped, pool within band of the anchor; trusted = fresh AND the anchor value
  unchanged for minPriceStable (new param, [60 s, 1 day], default 300 s). Guardian range used only when move > room.
  hedgeClipped cleared only by a lower report or an approval. Band measured against the reference.
- Consent (A''): onboard needs a permit that succeeds; a front-run permit is accepted only for the same signature
  (nonce - 1, deadline not passed, recovers to the owner, allowance == amount). No standing allowance is ever used.
- Lows: L-1, L-2, L-5, L-6, L-7, L-8, L-9, L-11, L-14, L-16 fixed; L-4, L-13, L-15 partly; L-3, L-10, L-12 acknowledged.

TASK 1: VERIFY THE STRUCTURAL FLOW-BOOKING CLAIM (highest priority)
The claim: "live - snapshot equals exactly what the client did, and since sync values it with the same function and
price as value(), no client action - inside or outside a module bracket, through upgraded account code, hooks, receive,
isValidSignature or executeFromExecutor - can change profit; only market moves on booked holdings, LP fee growth and
hedge equity change it."
1. Is every module write to snapAsset / snapBase / snapLiquidity equal to the true effect of the module's own call on the
   account, to the wei (or rounded against the client), on EVERY path? Compare SABook.lpAdd / lpRemove with what
   PositionManager / PoolManager actually do: slot0 read before vs. during the unlock, fee collection on increase /
   decrease / burn, SETTLE_PAIR / TAKE_PAIR / SWEEP / CLOSE_CURRENCY, native refunds, positions at tick boundaries,
   zero-liquidity positions, liquidity the client added to or removed from a tracked position directly.
2. Can account code make the module's computed effect differ from the real one in the client's favour (e.g. move slot0
   inside the bracket, re-enter PositionManager, run a second swap through SwapExecutor so the record is not the
   module's swap, write the transient record slots from another context)?
3. Is sync's valuation of live - snapshot really the same function as value()? Look for terms in one and not the other:
   uncollected fees, hedge equity, positions dropped (burned / transferred by the client), positions added by the client,
   rounding of negative base deltas, int256 snapshots below zero.
4. Can a flow be booked twice or never (pending forever while the anchor is never trusted; a position dropped while
   pending; revoke / re-register; MAX_POSITIONS)?
5. The fee: can profit as charged (min(V(anchor), V(pool)) - contributed after a trusted sync) exceed the client's real
   gain? Consider a keeper that walks the anchor within the window and holds it minPriceStable, a pool held displaced for
   minPriceStable, a multicall with reportPrice + chargeFee, hedge equity reports.
6. Our rebuttal of booking at min/max in the client's favour (response, Rebuttal 1): does the one-price design open a
   path the min/max design would have closed?
