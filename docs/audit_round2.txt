DESIGN RULES (do not report as findings; report if the code breaks them)
- Limits are relative to NAV or to the anchor, never small absolute caps, and must never block a withdrawal.
- Keeper = semi-trusted hot key. A compromised keeper's damage must stay within the per-channel bounds in
  DESIGN.md ("Compromised-keeper damage per day"). Keeper + guardian together are trusted.
- A budget never reverts settle: over-budget price/equity is clipped, redeems still go through.

TRUST MODEL CHANGES SINCE ROUND 1
- Price: settle requires the keeper price within poolBandBps (1.5%) of the pool; NAV uses the anchor lastPrice,
  which moves toward the report at most refDriftBps (10%) per decaying day, freely only inside guardian
  approvePrice(lo, hi, until) and on the first settle. Paused = anchor frozen. swap/mint/increase need the keeper
  price within the band of the pool AND of the anchor.
- Hedge equity: keeper alone may only lower it (hedgeStepBps x lastNav per decaying day); any increase needs the
  guardian's approveHedgeEquity(value, until), exact, epoch-bound, one-shot, cleared by margin send/return.
  sendHedgeMargin caps max(hedgeEquity, netMargin) + amount <= hedgeCapBps x lastNav.
- LP adds: paid = drop of held value at the anchor; got = liquidityValue at the anchor; revert unless
  got >= paid x (1 - maxSlippageBps); turnover charged paid x slippage / (band + slippage).
- Emergency: after 72 h without redeem-queue progress, anyone arms; execute >= 6 h later unless a settlement made
  progress. >= 1M gas per burn attempt. emergencyRedeem refused while positions are open, for up to 7 d.

LENSES REQUESTED (seven did not run in round 1; please run each explicitly)
1. Economic security: the cheapest end-to-end extraction for a compromised keeper with accomplice capital and pool
   pushes, over 1, 3 and 7 days, all channels at once (anchor walk, band skew, swaps/adds, hedge, fee). Does any combination beat the per-channel bounds in DESIGN.md, or the sum of them?
   Is the decaying budget compounding (relative anchor steps, e^x) larger than we state?
2. Execution trace: multi-call sequences in one block or one transaction (code-executing keeper / EIP-7702):
   settle -> swap -> mint -> settle; partial redeem fill + clipped settle + deposit cancel; arm -> settle that does
   not progress -> execute.
3. Periphery / native plumbing: native HYPE through PositionManager (SETTLE_PAIR, SWEEP), PoolManager sync/settle/
   take in unlockCallback, WHYPE unwrap, receive(), emergencyRedeem native leg; _heldValue on an increase that
   also collects fees.
4. First principles: is "paid vs value at the anchor" the right invariant for an LP add? Can a range be chosen
   whose value at the anchor passes while its value at the true price is much lower (wide vs narrow, out of range)?
5. Asymmetry: paths that differ by direction (price up vs down clip, hedge up vs down, sell base vs buy base,
   currency0 vs currency1 base) or by role (keeper vs guardian vs anyone); round-trip a value through them.
6. Boundary: ref == 0 first settle, budget exactly exhausted, dt = 0 and dt >= 1 day, approval at until, epoch
   wrap of hedgeApprovedEpoch (epoch + 1), supply 0 restart, redeem head partial fill with idle = 0 or 1 wei,
   gasleft exactly UNWIND_MIN_GAS, timelock ts == 1 (done) and expiry boundary.
7. Flow gaps: value that enters or leaves without passing a check (fees collected by increase/decrease, sweep
   leftovers, failed pushes to claimable, late hedge return after emergency, donations), and whether every keeper
   path keeps _checkReserve true.
